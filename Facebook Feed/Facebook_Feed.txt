Functional Requirement:
------------------------
- Publish a post; return its ID after durable storage.
- Return a page of ranked posts and a next-page cursor.
- Fetch an individual post.
- Delete a post and invalidate it in feeds.
- Follow a user or page.
- Unfollow a user of page.
- Analytics

Non-Functional Requirement:
----------------------------
- Low latency
- High availability
- Massive scale
- (And so on...)

Assumptions:
-------------
- Assuming 100M daily active users, each opening or refreshing the feed 10 times per day, and each author publishing one post per day.
-- Feed reads: 100M * 10 / 86400 = 11600 requests / second on average.
-- Feed writes: 100M / 86400 = 1160 posts / second on average.
-- At a 5x peak, plan for roughly 58K feed  reads / second and 5.8K post writes/ second.
-- If a response contains 20 posts, peak feed assembly may examine over 1M post references / second. We should batch post backups andspead requests across many stateless feed-service instances and storage shards.

API Design:
------------
POST /posts
GET /feed/cursor=...&limit=20
GET /posts/{postId}
DELETE /posts/{postId}
POST /users/{userId}/follow
DELETE /users/[userId}/follow
GET /analytics

DB Schema:
-----------
- Distributed NoSQL DB: Cassandra or others: {posts: post_id, author_id, body, media_ids, visibility, created_at, deleted_at}, {feed_entries: user_id, post_id, author_id, created_at, candidate_score}
- Graph DB or RDBMS: PostgreSQL or others (like Neo4j, etc.): {follows: follower_id, followee_id, created_at}
- Object Storage: AWS S3: For storing photos and videos outside the post DB.
- Distributed Cache: Redis: To reduce repeated reads of popular posts and feed pages.
